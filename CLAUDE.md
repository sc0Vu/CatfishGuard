# CLAUDE.md

## Project
**CatfishGuard** — a Manifest V3 Chrome extension that flags **recruiter/job
scams and phishing on LinkedIn**. (Name it `CatfishGuard` in `manifest.json`;
the internal `hrsc-` UI prefix can stay or migrate to `cfg-` — cosmetic.)
Vanilla JS, no build step, no framework, no bundler — loads unpacked.
It reads the recruiter message / profile / job post in view, scores it, and shows
a risk badge with the exact signals that fired.

It is a **defensive aid, not a verdict.** The output is always "here are the risk
signals, you decide," never "this person is a scammer." Keyword matching has false
positives by design (a real fintech recruiter says "blockchain"), so every score
ships with its reasons.

Owner reasons from first principles: on a design choice, name the governing
constraint (evasion, false-positive cost, permission surface, where the signal is
cheap vs expensive to fake) rather than copying another scam-detector.

## Non-negotiable invariants (stop and flag if a change would violate one)
1. **Local only.** Nothing about the page, the recruiter, or the user leaves the
   browser. The one network call is fetching the public blocklist (see §Signals).
   No telemetry, no analytics, no uploading page content.
2. **Never a record about a named person.** The extension matches scam
   *infrastructure* (domains, handles, wallet addresses) and message *text*. It
   never builds, stores, or ships a list of named individuals labelled "scammer" —
   that is defamation and targeting, and a public version is worse. A private,
   on-device "I flagged this profile" note is the only per-person memory allowed,
   and it never syncs or publishes.
3. **Flags, not verdicts.** Every surfaced score shows *why* (which phrases /
   indicators fired). No UI copy asserts someone is a scammer. Bands and reasons,
   never a confident accusation.
4. **Data, never code, from any external source.** MV3's CSP forbids remote code;
   honour it. External lists (the blocklist) are pure data. Terms are matched as
   **literal strings** (escape regex metachars — see `analyzer.js countTerm`);
   never compile a regex supplied by an external/public file (ReDoS risk, no JS
   regex timeout).
5. **Minimal permissions.** No broad `host_permissions`, no always-on scanning of
   arbitrary pages, no feature that transmits a visited URL off-device, without an
   explicit decision and (for off-device lookups) user opt-in. Default to
   `activeTab` / on-demand. Adding a permission is a deliberate act, not a
   convenience.
6. **Non-blocking UI.** The alert is injected DOM — never a modal, a browser
   notification, or anything that blocks the page. A false positive must never
   stand between the user and what they're reading.
7. **Validate external input.** Treat a fetched list as hostile: validate schema,
   clamp weights/counts into sane ranges, degrade to "ignored" on garbage. A bad
   file must never break scoring or freeze the page.

## Architecture / layout
```

                         (raw/gist.githubusercontent.com) send ACAO:*, so a
                         credential-less CORS GET from the worker suffices
src/
  psl.js                 Public Suffix List as one string literal (data only,
                         MPL-2.0), generated by tools/mk_psl.py; loaded before
                         analyzer.js. Never fetched at runtime.
  analyzer.js            the scoring engine (no deps). RULES = weighted keyword
                         categories; blocklist matching (our schema +
                         eth-phishing-detect schema); returns {score, band,
                         reasons[]}. Self-contained; attaches self.HRScam.
  content.js             extracts visible LinkedIn text + links, runs the analyzer,
                         renders the floating risk badge + reason panel. Debounced
                         MutationObserver + SPA-nav poll re-scan.
  background.js          service worker: fetch + cache the GitHub blocklist
                         (6h TTL), merge over the bundled seed, answer the content
                         script. Supports both blocklist schemas.
  popup.html / popup.js  settings: enable toggle, blocklist URL, refresh, re-scan,
                         photo-search toggle, last-result for the active tab,
                         "Customize rules…" (opens options).
  options.html / .js     local rule overrides (roadmap #5): weights/caps/off,
                         extra + muted phrases, user brands, trusted domains,
                         live preview, import/export/reset. Stored in
                         chrome.storage.local `overrides`; validated by
                         analyzer normalizeOverrides().
  styles.css             injected UI; light/dark; hrsc- prefixed; high z-index.
data/
  blocklist.seed.json    bundled empty-but-valid seed (infrastructure only, no
                         names); merged under the remote list so it works offline.
icons/                   icon16/48/128 (generated by tools/mk_icons.py)
tools/mk_icons.py        icon generator, stdlib only (zlib+struct), no Pillow
tools/mk_psl.py          vendors + validates the PSL into src/psl.js (npm run psl)
test/                    node:test unit tests (analyzer, background) + e2e/
```

## Signals — two kinds, matched to how evadable they are
**1. Keyword score (bundled, in `analyzer.js RULES`).** Weighted categories:
`credentials` (seed phrase / wallet-connect / passport / bank — near-certain),
`offplatform` (Telegram/WhatsApp push), `money` (fees, deposits, task-payment,
USDT), `crypto` (web3/defi/rwa bait — has a cluster bonus: 3+ distinct terms
→ +20), `toogood` (unrealistic pay / no process), `pressure` (urgency/secrecy),
`devlure` (GitHub/coding-test outreach — weak, real recruiters say it),
`execlure` (run/clone/install/driver/paste-a-command — strong), a `pattern`
bonus for crypto + (execlure | devlure + pressure) — the fake-interview
campaign — plus `counter` legit signals (ATS hosts, "interview process") that
soften the score only when nothing near-certain fired (credentials, blocklist,
impersonation). Rules cover English + Chinese.

**1b. Domain module (bundled, `analyzer.js` domainReasons).** Registrable
domain via the bundled PSL; `impersonation` (lookalike/typo/homograph/brand-in-
subdomain vs bundled `BRANDS` = 35; claimed employer with no link to its domain
= 15; cap 60) and `linkrisk` (exe 40, IP/userinfo 25, archive 15, shortener/
punycode/free-mail 10, cheap TLD/free hosting 5; cap 40). `fuzzy:false` brands
(common words) are only matched exactly. Claim regexes are compiled from our
own escaped brand names only. Each category is capped so one can't
dominate. Bands: **0–29 low / 30–59 caution / 60–100 high**. A blocklist hit or a
credential/wallet request pushes to high on its own.

**2. Blocklist (remote, in `background.js`).** Infrastructure indicators only —
domains, URLs, off-platform handles, wallet addresses, throwaway emails — fetched
from a GitHub raw URL set in the popup, cached, merged over the bundled seed.
Accepts this project's schema and MetaMask `eth-phishing-detect`
(`blacklist`/`fuzzylist`). Prefer **reusing existing maintained lists** over
hand-rolling one.

**Why this split:** keywords change slowly and are the *most evadable* signal
(a public list is a cheat sheet for scammers, who just swap vocabulary), so they
stay **bundled** — public in the repo as source, compiled into each release, never
fetched at runtime. Infrastructure changes fast and is *hard to evade* (a scammer
can't cheaply change the wallet money lands in), so it stays **remote**. Do NOT
add a runtime `rules.json` fetch for keywords — decided against (evasion + tamper
surface + complexity for the weakest signal).

## Current state vs planned
**Built:** keyword analyzer, blocklist fetch/merge, LinkedIn extraction, popup
settings, and roadmap #1:
- each open conversation / overlay / page is scored as its own **unit**;
- a **thin banner pinned above each open conversation** (caution/high only),
  dismissible per conversation — the dismissal stores a *hash* of the thread id
  + band on-device and re-shows only if the band escalates (overlays: memory only);
- **dots in the conversation list** (open thread's full score, else a
  keyword-only score of the preview; `You: …` previews are never scored);
- **inbound-only scanning**: when events carry `msg-s-event-listitem--other`,
  only those are scored; otherwise it falls back to the whole thread and the
  panel says so;
- the **corner badge** + panel stays as the fallback (worst unit; banner "Why?"
  opens it). All LinkedIn selectors live in `SEL` at the top of `content.js`.
  **Thread selectors verified against live LinkedIn (2026-11):** message list,
  `--other` sender marker, `.msg-form` composer, and the list sitting in a
  *column-reverse* container (so the banner anchors before
  `.msg-s-message-list-container`). `test/e2e/fixtures/messaging-zh.html` is an
  anonymised copy of that structure. **Conversation list verified too:** rows
  have *no* thread link; the open row is marked
  `msg-conversations-container__convo-item-link--active`, so its dot uses the
  open thread's full score; previews are `Name: …` / `You: …` / `InMail • …`.
  Message hover chrome (`.msg-s-event-listitem__actions-container`) and
  `.a11y-text` are excluded from scoring. **Messaging-list popup verified:**
  `.msg-overlay-list-bubble` uses div rows (`.msg-overlay-list-bubble__convo-item--v2`)
  and `.msg-overlay-list-bubble__message-snippet--v2` previews. **Open chat
  popup verified (inner structure):** same message list / `--other` / `.msg-form`
  markup as the full thread; expanded state is the header button
  `.msg-overlay-conversation-bubble__expand-btn[aria-expanded]`, which is what
  minimise detection keys on (the `--is-minimized` class is kept as an unverified
  fallback). Popups without a message list are not scored. **Full chat popup
  on the feed verified (2026-11):** `test/e2e/fixtures/feed-overlay-zh.html`
  is an anonymised copy (sender names on every event; the user's own links
  unroll into `update-components-article` cards, which stay out of the score).
  The bubble also carries `data-msg-overlay-conversation-bubble-is-minimized`
  — a candidate minimise signal if the expand button ever changes.
- **Feed chat popups live in a shadow root (verified live 2026-11):** on
  `/feed` LinkedIn renders the chat popups and messaging list inside the open
  shadow root of `div#interop-outlet` (a hidden `/preload/` iframe holds a
  second copy; it is ignored, content script stays top-frame only). All
  LinkedIn queries go through `qs`/`qsa` over `roots()` (document + shadow
  roots of `SEL.shadowHosts` and of `<body>`'s direct children, opened via
  `chrome.dom.openOrClosedShadowRoot`). Each root is observed and gets our
  stylesheet as an adopted sheet; the CSS text comes from the service worker
  (`cfg:css`), **not** a `web_accessible_resources` entry, which pages could
  probe to detect the extension. Test: `/feed/zh-shadow` mode of
  `feed-overlay-zh.html`.
- **List dots survive leaving a conversation:** rows have no thread id, so a
  scored conversation is matched back to its row by sender display name
  (`.msg-s-message-group__name` in `--other` events ↔ `…participant-names` on
  the row, verified live 2026-11). Held as a *hash* in memory only; a worse
  newer preview can raise a dot, never lower it.
- **"Conversations with risk signals in this tab"** list in the corner panel
  (opened conversations + caution/high previews). Memory only, shows the
  display name LinkedIn already shows, copy is "risk signals", never stored
  (invariant 2). "Show in list" only scrolls; it never reorders LinkedIn's list.
- **Layout-health check** (`checkHealth` in `content.js`): after a 5 s
  post-navigation grace, missing conversation list / row names / message list /
  message events / sender names → "!" on the badge, a warning box in the panel
  and the popup, and the corner shows even when nothing was scored. Purpose: a
  LinkedIn redesign must read as "can't read this page", never as "no risk".
- Keyword rules cover **English + Chinese (simplified/traditional)**. Term
  boundaries are CJK-aware: Han/Kana/Thai characters never act as a boundary
  barrier.
- **Reference case (live, 2026-11):** the GitHub-sourced "fake interview"
  pattern (web3 role, free scheduling link, "the lead is waiting in the
  meeting") scored 13 on keywords alone; devlure + the pattern bonus lift it to
  38 (caution), and with the claimed brand in `BRANDS` (peaq, added from this
  report) to 53. It stays below *high*: no payment/credential ask. See the zh
  analyzer tests.

## Roadmap (build in this order; each is additive)
1. ~~Thread banner + conversation-list dots + sender-scoped scanning~~ — built
   (above); thread, list, list popup and open chat popup verified live.
2. ~~**Domain / brand-impersonation module**~~ — built (§1b). Next steps: grow
   `BRANDS` from real reports; consider the user's *own* employer-domain hints.
   Original spec: the high-value, hard-to-evade signal.
   Claimed-employer vs the registrable domain of each link (needs a bundled Public
   Suffix List so `google.com.evil.ru` resolves to `evil.ru`), lookalike /
   typosquat / homograph against a bundled impersonated-brand list, URL risk
   heuristics (IP, punycode, shorteners, cheap TLDs, `@`), free-email-as-corporate.
3. ~~**Reverse-image-search button**~~ — built: Google Lens / TinEye *links* in
   the corner panel (not injected into LinkedIn's layout) for the other
   person's photo (`img.msg-s-event-listitem__profile-picture` inside an
   `--other` event; largest licdn profile photo on `/in/` pages). Only
   `*.licdn.com` profile-photo URLs are offered; `rel=noopener noreferrer` +
   `referrerPolicy=no-referrer`; nothing sent unless clicked; `photoSearch`
   setting (default on) hides it; disclosed in PRIVACY.md. No new permission.
   Caveat: AI-generated faces defeat it — the copy says so.
4. **Page-check / phishing module — DEFERRED, needs care.** Detect a fake
   meeting/interview landing page: brand-claim vs actual domain + credential/PII
   form + URL heuristics, optionally an opt-in reputation feed (community lists or
   Safe Browsing). **Gated on the permission model:** on-demand `activeTab`
   ("Check this page" button), NOT broad always-on host permissions. Reputation
   lookups send the URL off-device → opt-in only. Positioned as recruiter-specific
   + explainable, not a replacement for the browser's own Safe Browsing.
5. ~~**Optional local override page**~~ — built (`src/options.*`). Overrides are
   passed to `analyze(text, links, {overrides})` and compiled/cached there;
   `normalizeOverrides` clamps weights (credentials min 20, negatives only for
   `counter`), caps phrases (100/category, 300 total, 2–80 chars, literal),
   refuses disabling/muting `credentials`, reduces brands/trusted entries to
   registrable domains. Floors (credential 60, blocklist 60) aren't overridable.
   `result.custom` drives the "Custom rules active" note. Domain-module weights
   (impersonation/linkrisk/pattern) are not user-tunable yet.
   Step 4 (page check) was skipped by the owner for now.

**Backlog (noted, not scheduled):**
- **Claimed employer vs sender's own headline.** Pull the claimed company from
  inbound messages ("I'm a … at X", "recruiter for X", "on behalf of X",
  "我是 X 的…", "来自 X") and compare it with the headline LinkedIn already
  shows in the thread header (`.msg-entity-lockup__entity-info`, verified
  live). If the headline doesn't mention X, add a +15 reason: "Says they recruit
  for X, but their LinkedIn headline doesn't mention X". Synchronous and local:
  it reads only what's on screen; no profile fetch, nothing stored (invariant 2).
  Low weight because headlines are self-written (cheap to fake) and real
  recruiters often have generic headlines or recruit for clients. Motivating
  case: the anonymised zh fixture (claims a web3 company; headline is "Project
  Manager | …"), which would go 38 → 53.

## Honest limits (keep the UI and claims aligned with these)
- It's a heuristic. False positives and negatives both happen; the reasons are
  what make it useful, not the number.
- A public keyword list is evadable by construction; the strongest signals are the
  infrastructure blocklist and the domain-impersonation check.
- The phishing module would partly duplicate Chrome Safe Browsing — its edge is
  catching fresh recruiter-campaign domains and *explaining why*.
- The real control is behavioural: never enter credentials/PII on a page reached
  via a link; verify the recruiter through the company's own channel. The tool's
  job is to raise the flag loudly enough that the user stops and does that.

## Store & privacy policy (PRIVACY.md — required)
The Chrome Web Store requires a **privacy policy** for any extension that handles
user data, and CatfishGuard reads page content — so a `PRIVACY.md` is mandatory,
hosted at a public URL and linked in the Developer Dashboard → Privacy tab. Keep
it in sync with what the code actually does; a policy that under-discloses is a
takedown risk.

What CatfishGuard's policy must state (and today these are all true, which is the
selling point — keep them true):
- **What it accesses:** the visible text and links of LinkedIn pages you view, to
  compute a risk score **locally in the browser**.
- **What leaves the device:** nothing about you or the pages you view. The only
  outbound request the extension makes is a GET to the **public blocklist URL**
  you configure (GitHub raw); it carries no page content and no personal data
  (only the unavoidable request metadata any fetch has, e.g. your IP, seen by
  that host). The reverse-image-search links send a LinkedIn photo URL to Google
  Lens / TinEye **only when the user clicks one** (user-initiated navigation,
  no referrer) — keep that disclosed.
- **Storage:** settings and the blocklist cache live in `chrome.storage.local`,
  on-device, not synced, never transmitted.
- **No** analytics, tracking, ads, selling or sharing of data. Single purpose:
  flagging recruiter scams/phishing.
- **Permissions justification** (the store asks per-permission): `storage`
  (settings + cache), content script on `*.linkedin.com` (read the page to score
  it). There is no host permission: the blocklist is a public CORS-readable
  file on GitHub. If GitHub ever drops `Access-Control-Allow-Origin: *`, the
  fetch fails gracefully ("Last update failed"); re-adding a host permission is
  then a deliberate decision (invariant 5), not a silent fix.

**Keep the policy and the code honest together:** the deferred roadmap items (§5
reputation lookups, the phishing page-check) would transmit visited URLs
off-device. Those are **opt-in** and the privacy policy AND the store data-use
disclosures must be updated *before* shipping them — adding that behaviour
silently under an unchanged policy is a policy violation. Also complete the
Dashboard's **Data Use** certifications (limited use, no sale) to match PRIVACY.md.

## Dev / build / run
- No build step. `chrome://extensions` → Developer mode → **Load unpacked** →
  the extension folder.
- Reload the extension after editing; the content script re-injects on next page
  load. Use the popup's **Re-scan** during iteration.
- Icons: regenerate with `npm run icons` (`tools/mk_icons.py`, stdlib only) if the shield changes.
  Teal shield + catfish; deliberately not LinkedIn's blue. 128px has the
  store's 16px transparent padding.
- Release zip: `npm run package` (`tools/package.py`) → `dist/catfishguard-<ver>.zip`
  with only manifest + src/ data/ icons/; checks manifest refs and that
  manifest/package.json versions match; reproducible bytes.
- GitHub Release: push a `vX.Y.Z` tag matching manifest `version` →
  `.github/workflows/release.yml` runs unit tests, builds the zip and attaches
  it to the release (manual "Run workflow" with a tag for existing tags). The
  Chrome Web Store upload stays manual. Actions pinned to commit SHAs.
- Analyzer is testable in isolation with Node via a `vm` sandbox that provides
  `self` + `URL` (`test/helpers.js`). `npm test` runs unit tests; `npm run test:e2e`
  loads the real extension in headless Chrome. Add a case per new category or
  rule; assert expected scores derived by hand, never mirror current output.

## Conventions
- Vanilla JS, no framework/bundler. Keep `analyzer.js` dependency-free and pure
  (text + links + blocklist in → score out) so it stays unit-testable.
- UI classes are `hrsc-` prefixed; never leak styles onto LinkedIn's DOM.
- Wrap every `chrome.storage` / message call so a failure degrades gracefully
  (the extension must never throw into the page).
- Honest copy: the panel says "risk signals," "a prompt to look closer," never
  "scammer." Any new surfaced claim gets the same treatment.
- Commits: one logical change each; conventional-commit subjects.
